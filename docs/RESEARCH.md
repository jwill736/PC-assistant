# Rebuild Jarvis's ears before giving it hands

The weakest part of this assistant is its hearing, not its Claude brain: an energy gate feeding Whisper `base.en`, with the wake word matched on the transcript, is two generations behind the 2026 open-source consensus of a self-trained acoustic wake-word model, Silero VAD v6 and a streaming recognizer. Swapping `base.en` (about 10.3% average word error rate, WER) for Moonshine Small or Medium Streaming (7.84% or 6.65%, MIT, CPU-only) cuts the time from end of speech to text from seconds to 165–269 ms on a desktop CPU ([Moonshine paper](https://download.moonshine.ai/docs/moonshine_streaming_paper.pdf); [Moonshine vs Whisper](https://moonshine-voice.readthedocs.io/en/latest/moonshine-vs-whisper/)). On a PC with an NVIDIA GPU, Parakeet TDT 0.6B runs through `onnx-asr` at hundreds of times real time ([onnx-asr](https://github.com/istupakov/onnx-asr)). Custom trigger words should be trained with livekit-wakeword (Apache-2.0), which exports openWakeWord-compatible ONNX models and reports 0.08 false accepts per hour on its own benchmark. The two familiar alternatives are now closed off: Picovoice Porcupine's free tier ended on June 30, 2026, and openWakeWord's pretrained models are licensed for non-commercial use only ([livekit-wakeword](https://github.com/livekit/livekit-wakeword); [Home Assistant forum](https://community.home-assistant.io/t/fyi-picovoice-confirmed-free-tier-accesskeys-will-stop-working-after-june-30-2026/1012744)). "Respond only to my voice" can be built as a stack of filters: a wake-word verifier, WeSpeaker speaker embeddings via `speakeronnx`, an echo gate with a check against the text being spoken, and WebRTC acoustic echo cancellation (AEC3) using the speaker output as a reference. It remains a convenience filter, though: a replayed clip of the owner's own stream can defeat it, so consequential actions still need confirmation. For controlling the PC, every serious Windows agent project (Microsoft UFO², WindowsAgentArena, Agent S3) arrives at the same order of deterministic APIs first, the UI Automation (UIA) accessibility tree second and screenshots last, where Claude's `computer_toolset_20260801`, already supported by the configured `claude-opus-5`, serves the long tail behind per-action confirmation because prompt injection from on-screen content is still unsolved ([Claude computer use docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool.md)). For streaming, the gains lie in obs-websocket's event stream and unused requests, Twitch EventSub with a device-code public client, and Streamer.bot's `DoAction` API as a multi-platform layer. The build list at the end orders this work into five phases starting with hearing, because owner verification, trigger words and safe PC control all depend on hearing the right person quickly and reliably.

## Open-source assistants converge on the same six patterns

In September 2026 the credible open-source ecosystem falls into two groups. The platform projects, Home Assistant Assist with its Wyoming protocol and satellites and the Mycroft successors OVOS and Neon, are maintained but built for Linux home servers: the OVOS installer supports only Linux and macOS ([ovos-installer](https://github.com/OpenVoiceOS/ovos-installer)), and Mycroft-core, both Rhasspy versions and wyoming-satellite are archived ([mycroft-core](https://github.com/MycroftAI/mycroft-core); [wyoming-satellite](https://github.com/rhasspy/wyoming-satellite)). The momentum sits with LLM-first companions and agents such as AIRI (~48.7k stars), Leon 2.0 (~17.6k), Open-LLM-VTuber (~13.5k) and GLaDOS (~5.6k) ([AIRI](https://github.com/moeru-ai/airi); [Leon](https://github.com/leon-ai/leon); [Open-LLM-VTuber](https://github.com/Open-LLM-VTuber/Open-LLM-VTuber); [GLaDOS](https://github.com/dnhkng/GLaDOS)). None can be adopted wholesale on a single Windows PC, but their code and issue trackers amount to a free design review.

Most "JARVIS" repositories are tutorial-grade. The closest public analog to this project is sosoj92/jarvis-assistant-vocal, which targets Windows 11, switches between Claude + ElevenLabs and Ollama + Piper with one config line, uses openWakeWord, local Whisper and OBS control, and exposes an MCP server ([jarvis-assistant-vocal](https://github.com/sosoj92/jarvis-assistant-vocal)). It is worth reading, but at ~125 stars and under two months old it should not become a dependency.

Six patterns recur across these codebases, and each maps onto a gap in the current app. The first is an **ordered intent pipeline**: Home Assistant's "prefer handling commands locally" runs a deterministic sentence matcher before the LLM ([HA Voice Chapter 9](https://www.home-assistant.io/blog/2025/02/13/voice-chapter-9-speech-to-phrase/)), and one writer found "95% of my commands are simple and repetitive", handled by intents that "get things right 100% of the time" ([XDA](https://www.xda-developers.com/gave-home-assistant-local-llm-voice-control-turned-off-most-what-say/)). The existing router already does this; the lesson to add is sharing the router's history with Claude so follow-ups can refer to fast-path actions, as HA now does. The second is OVOS's **utterance corrections** step, which rewrites recurring mis-hearings before intent matching and is a cheap fix for invented names such as OBS scene titles. The third is **sentence-by-sentence streaming from LLM to TTS**, which cut HA's time to first audio on long replies from more than 5 s to about 0.5 s ([HA Voice Chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11/)).

The fourth is an **explicit turn state machine**. voice2 gives every utterance a `turn_id` so that "replies to an interrupted turn are discarded at every stage" ([voice2](https://github.com/AIIT-GLITCH/voice2)), and Open-LLM-VTuber cancels the conversation task on interrupt and records only the text actually spoken, followed by "[Interrupted by user]". The fifth is **two-lane scheduling**: in GLaDOS "Your speech jumps the queue ... User always wins" over the autonomy loop, and Open-LLM-VTuber tags proactive speech `skip_memory` so unsolicited remarks never pollute history. The sixth is a **single orchestrator**: Wallie-V2's early prototypes had parallel generation paths and the bot "would repeat itself, contradict", so everything moved to one path with one message history ([wallie-V2](https://github.com/cpiprint/wallie-V2)). Continued conversation belongs in the same family. HA users filed bugs when the LLM asked a question while the mic stayed closed, and the proposed fix was a structured "follow-up expected" flag ([home-assistant/core #137450](https://github.com/home-assistant/core/issues/137450)), a better trigger for the current 8-second follow-up window than a fixed timer or a trailing question mark.

The failure modes are just as consistent. **Self-hearing is the worst**: a NousResearch agent with an RMS-only barge-in gate transcribed its own TTS for "at least seven consecutive self-captured turns", and the fix that shipped drops anything heard during playback that closely matches the text being spoken, with a 10-character evidence floor so genuine interjections such as "yes" survive ([hermes-agent #75780](https://github.com/NousResearch/hermes-agent/issues/75780)). Chattiness is second: one user's Qwen3 "think mode" had Piper "still reading out the LLM's internal monologue" five minutes later ([Joe Karlsson](https://www.joekarlsson.com/blog/local-voice-ai-home-assistant-gpu/)), and another found that false activations made the LLM end every reply with a question, creating a loop ([HA community](https://community.home-assistant.io/t/my-journey-to-a-reliable-and-enjoyable-locally-hosted-voice-assistant/944860)). Tool reliability is third: Llama-3.2-3B, asked to turn off the kitchen, generated turn-offs for the whole house including the front-door lock ([TechFuelHQ](https://techfuelhq.com/tutorials/home-assistant-local-llm-voice-2026/)), while one builder found Claude "follows HA's tool calling format correctly every time" ([Joe Karlsson](https://www.joekarlsson.com/blog/local-voice-ai-home-assistant-gpu/)), which is why the brain is not where this stack falls short. On Windows the pain concentrates in faster-whisper's CUDA 12 and cuDNN 9 DLLs, with `cublas64_12.dll` not found and cuDNN handle failures ([faster-whisper #1276](https://github.com/SYSTRAN/faster-whisper/issues/1276); [#1279](https://github.com/SYSTRAN/faster-whisper/issues/1279)), and setup cost is real: one builder needed "more than two weeks" to get a local stack running reliably ([HowToGeek](https://www.howtogeek.com/built-a-voice-assistant-faster-than-alexa-completely-private/)).

## A four-stage front end cuts command latency from seconds to about half a second

### Porcupine is gone, so train the name and trigger words yourself

Picovoice's free tier ended on June 30, 2026. Its SDK will not start without a valid AccessKey, and Picovoice says "There is no non-commercial tier planned" ([HA forum](https://community.home-assistant.io/t/fyi-picovoice-confirmed-free-tier-accesskeys-will-stop-working-after-june-30-2026/1012744); [Picovoice FAQ](https://picovoice.ai/docs/faq/general/)).

openWakeWord remains the de facto model format. It works on **80 ms frames** and uses a shared, frozen embedding model, so one Raspberry Pi 3 core can run 15–20 wake-word models. It targets **under 5% false rejects and under 0.5 false accepts per hour**, and on Windows it runs through onnxruntime only. However, its last release was February 2024, and **all of its bundled pretrained models, including "hey jarvis", are CC BY-NC-SA (non-commercial)** ([openWakeWord README](https://github.com/dscripka/openWakeWord); [PyPI](https://pypi.org/project/openwakeword/)).

The better trainer is **livekit-wakeword** (Apache-2.0, April 2026). It keeps openWakeWord's audio features, replaces the classifier head with a conv-attention network, and runs voice synthesis, augmentation, training and ONNX export from one YAML file. On LiveKit's own "hey livekit" benchmark it cut false positives from **8.50 to 0.08 per hour** while raising recall from **68.6% to 86.1%** ([livekit-wakeword](https://github.com/livekit/livekit-wakeword); [LiveKit blog](https://livekit.com/blog/livekit-wakeword)). That is a vendor-run result on the vendor's own phrase, and nobody has replicated it independently.

Exported models are drop-in openWakeWord ONNX files, so running them on Windows needs only onnxruntime. The training pipeline is documented for Linux and macOS, so run training on WSL or Colab. Community practice is a few thousand Piper-generated positive clips plus openWakeWord's ~4 GB negative dataset, and about 1–2 hours of work ([HA forum](https://community.home-assistant.io/t/fyi-picovoice-confirmed-free-tier-accesskeys-will-stop-working-after-june-30-2026/1012744)).

Two fallbacks exist. microWakeWord models run from Python on Windows via the `pymicro-wakeword` wheel ([PyPI](https://pypi.org/project/pymicro-wakeword/)). EfficientWord-Net enrolls from 4–10 user recordings with no training step, but its own README admits performance "notably lower compared to Porcupine", and it handles only single words ([EfficientWord-Net](https://github.com/Ant-Brain/EfficientWord-Net)).

Custom trigger words should work in two tiers. **Soft triggers** are what the app already has, fuzzy matching on the transcript, now fed by a much better recognizer with the phrase loaded as a keyterm, so a word typed into the HUD works within seconds. **Hard triggers** are trained acoustic models, and they matter for three kinds of phrase: the assistant's name, so STT no longer has to run on every sentence just to find it; a "stop" word that must fire while TTS is playing; and zero-LLM stream commands such as "clip that", which must act instantly.

Home Assistant validated this design. It now maps separate wake words to separate pipelines: "Okay Nabu" goes to a local one and "Hey Jarvis" to a cloud LLM ([HA Voice Chapter 11](https://www.home-assistant.io/blog/2025/10/22/voice-chapter-11/)). A stop wake word was one of the features that pushed HA to a new satellite protocol ([wyoming-satellite](https://github.com/rhasspy/wyoming-satellite)). Extra models share the openWakeWord feature extractor, so each additional hard trigger costs little CPU. The HUD can let the owner type a phrase, use it right away as a soft trigger, and promote it to a hard trigger after a background training run.

For the name, keep the transcript check as a second stage. Require the acoustic model to fire and the transcript to start with the name. This mirrors the two-network design of openWakeWord's own "hey jarvis" model ([hey_jarvis model doc](https://github.com/dscripka/openWakeWord/blob/main/docs/models/hey_jarvis.md)). Anchoring to the start of the utterance matters more for a streamer than for anyone else. The owner will say "Jarvis" to chat all the time, and no speaker verifier can tell the owner talking *about* the assistant from the owner talking *to* it.

### Silero VAD v6 replaces the energy gate

Silero VAD v6 (MIT, pip `silero-vad` 6.2.3) processes a 30+ ms audio chunk in **under 1 ms on one CPU thread**, using a ~2 MB model. It runs under ONNX Runtime without PyTorch ([silero-vad](https://github.com/snakers4/silero-vad); [PyPI](https://pypi.org/project/silero-vad/)).

On Silero's 17-hour multi-domain benchmark, v6 scores **0.97 ROC-AUC**. On noise-only ESC-50 clips it scores **0.87 correct "no speech" verdicts**, against 0.42 for TEN VAD and 0 for WebRTC VAD ([Silero quality metrics](https://github.com/snakers4/silero-vad/wiki/Quality-Metrics)). That noise rejection is what matters on a PC playing game audio and music. Every non-speech segment that reaches Whisper risks a hallucination; the current listener already keeps a blocklist of phantom phrases such as "thanks for watching".

FireRedVAD (Apache-2.0) wins its own multilingual benchmark, with F1 97.57 against Silero's 95.95 ([FireRedVAD](https://github.com/FireRedTeam/FireRedVAD)). Each vendor wins its own test, though. TEN VAD's licence also forbids uses that compete with Agora ([TEN VAD licence](https://github.com/TEN-framework/ten-vad/blob/main/LICENSE)). Silero is the default.

GLaDOS's tuned settings are a good starting point: 32 ms chunks, an 800 ms buffer of audio kept before activation so first syllables are not clipped, and a 640 ms silence endpoint ([GLaDOS README](https://github.com/dnhkng/GLaDOS/blob/main/README.md)). To shorten endpoints further without cutting people off mid-thought, Pipecat pairs a 0.2 s VAD stop with **Smart Turn v3**. Smart Turn v3 is an 8 MB int8 ONNX end-of-turn model (BSD-2-clause) that takes **12.6–17.7 ms on a CPU** ([Daily blog](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/); [Pipecat docs](https://docs.pipecat.ai/api-reference/server/utilities/turn-detection/smart-turn-overview)). Compared with the current 800 ms silence timeout, that alone removes more than half a second from every turn.

### Moonshine on CPU, Parakeet on NVIDIA, Whisper only as a fallback

Whisper Base averages **10.3% WER** on the Open ASR benchmarks ([Moonshine paper](https://download.moonshine.ai/docs/moonshine_streaming_paper.pdf)). Moonshine's streaming models use a sliding-window encoder, which has two effects. The time to the first word stays bounded however long the utterance is, and transcription happens while the user is still speaking. That is why the gap between the VAD marking an utterance complete and the transcript arriving is **165 ms (Small) and 269 ms (Medium)** on a Linux x86 CPU. On the same machine, Whisper Tiny takes 1,141 ms and Whisper Small 3,425 ms ([Moonshine vs Whisper](https://moonshine-voice.readthedocs.io/en/latest/moonshine-vs-whisper/)).

Two caveats apply before switching. First, Moonshine's numbers are its own measurements on an unnamed x86 CPU. A GitHub report measured about 11.8% WER through the streaming chunk path, against the paper's float-model reference. Moonshine responded with a script that compares the two paths, and it should be run on the owner's own audio before committing ([eval-librispeech.py](https://github.com/moonshine-ai/moonshine/blob/main/scripts/eval-librispeech.py)). Second, sherpa-onnx, the other common Parakeet runtime, has an open report of Parakeet TDT returning empty text on Windows 11 ([sherpa-onnx #3767](https://github.com/k2-fsa/sherpa-onnx/issues/3767)), which is why `onnx-asr` is the recommended route. Keep faster-whisper as a configurable fallback. Add a startup doctor check for `cublas64_12.dll` and the cuDNN 9 DLLs, and pick the tier automatically from the detected hardware.

### Bias recognition with the PC's own vocabulary

Every recommended engine can be biased toward specific words without retraining, and the app already discovers installed programs. Moonshine's `set_keyterms()` changes a word-boost list mid-stream; at the default boost it cut Medium's error rate on the listed terms from **7.89% to 5.58%**, while error on other words moved only from 3.90% to 3.93% ([Moonshine domain customization](https://github.com/moonshine-ai/moonshine/blob/main/docs/models/domain-customization.md)). sherpa-onnx supports hotwords only for transducer models under `modified_beam_search` ([sherpa-onnx hotwords](https://k2-fsa.github.io/sherpa/onnx/hotwords/index.html)). faster-whisper's `hotwords` parameter is weaker than its name suggests: it is not a beam-search boost, because the source code simply inserts the words into the prompt slot, capped at half the context ([transcribe.py](https://github.com/SYSTRAN/faster-whisper/blob/master/faster_whisper/transcribe.py)).

Feed the recognizer the assistant's name, the trigger phrases, Start Menu app names, and the live OBS scene and source names. Refresh the list on OBS scene events. Then run a fuzzy match against the same list before routing, in the spirit of OVOS's corrections step.

## Owner-only listening is a stack of filters, not one model

### Speaker embeddings: WeSpeaker models via speakeronnx

Modern open speaker-embedding models all reach roughly **0.5–1% equal error rate (EER)** on the VoxCeleb1-O benchmark with full-length clips. What separates them for this app is ease of use on Windows, licence, and behaviour on short utterances.

| Model | VoxCeleb1-O EER | Size | Licence | Runtime |
|---|---|---|---|---|
| WeSpeaker ResNet34-LM | 0.867% (plain cosine), 0.723% with score normalization | 6.63M params, 25.3 MB ONNX | CC-BY-4.0 | `speakeronnx`, sherpa-onnx |
| WeSpeaker CAM++ | 0.803% (plain cosine), 0.659% with score normalization | 7.18M params, 27.9 MB ONNX | CC-BY-4.0 | Same; single-thread real-time factor 0.013 |
| SpeechBrain ECAPA-TDNN | 0.80% | ~20.8M params | Check the model card | PyTorch |
| NVIDIA TitaNet-Large | 0.66% | 23M params, 96.7 MB ONNX | CC-BY-4.0 | NeMo or ONNX export |
| Resemblyzer | Not published | — | Apache-2.0 | 2019-era fallback |

Sources: [WeSpeaker results](https://github.com/wenet-e2e/wespeaker/blob/master/examples/voxceleb/v2/README.md); [sherpa-onnx speaker models](https://github.com/k2-fsa/sherpa-onnx/releases/tag/speaker-recongition-models); [CAM++ paper](https://arxiv.org/html/2303.00332v3); [SpeechBrain card](https://huggingface.co/speechbrain/spkrec-ecapa-voxceleb); [TitaNet card](https://huggingface.co/nvidia/speakerverification_en_titanet_large); [Resemblyzer](https://github.com/resemble-ai/Resemblyzer).

`speakeronnx` (Apache-2.0, June 2026) is pure onnxruntime with no PyTorch. It auto-downloads nine models and recommends **5–30 s of enrollment audio per speaker**. Its example scores are about 0.82 for the same speaker against 0.21 for a different speaker at a 0.45 threshold ([speakeronnx](https://pypi.org/project/speakeronnx/)). CAM++'s single-thread real-time factor of 0.013 works out to about 26 ms of CPU time for a 2 s clip, negligible next to STT.

OVOS already ships this exact pattern as `ovos-ww-verifier-plugin-speaker`. After the wake word fires, it embeds the audio, compares it with enrolled profiles, and "Activations from unrecognised speakers are silently dropped". It defaults to a cosine threshold of 0.45 for `wespeaker-resnet34`, supports per-profile thresholds, and fails open until someone enrolls. Its end-to-end tests use synthetic edge-tts voices as impostors ([OVOS plugin](https://github.com/OpenVoiceOS/ovos-ww-verifier-plugin-speaker)). The plugin also warns that cosine scales differ between architectures. SpeechBrain's default threshold is 0.25 ([speechbrain speaker.py](https://github.com/speechbrain/speechbrain/blob/develop/speechbrain/inference/speaker.py)), so any threshold must be retuned whenever the model changes.

Short commands are the hard case. For a ResNet34 model on VoxCeleb1-O, **EER rises from 1.45% on full clips to 1.59% at 5 s, 2.74% at 2 s and 6.77% at 1 s**. On far-field VOiCES recordings it reaches 16.96% at 1 s ([Gusev et al.](https://arxiv.org/html/2002.06033v1)). A hard reject on a bare "yes" will therefore fail often. The fix is to verify the whole wake-word-plus-command audio rather than the wake word alone, to open a continuation window after a verified turn in which short replies are accepted, and to raise the threshold only while TTS is playing.

Enrollment should mix free speech with wake-phrase takes. On short-phrase verification, combining free-speech and fixed-phrase enrollment performed best, reaching **1.6% EER at 10 s** of enrollment ([VoxPhrase](https://arxiv.org/html/2606.16115v1)). An open ECAPA voice-login project stores every enrollment sample and scores new audio as 60% top-2 average plus 40% centroid similarity ([Voice-Login-ECAPA-TDNN](https://github.com/kinhluan/Voice-Login-ECAPA-TDNN)).

openWakeWord's custom verifier is a useful cheap first filter, placed before the embedding check. It is a tiny logistic-regression model trained from at least 3 wake-word takes and about 10 s of the owner's other speech. Past false activations make some of its most effective negative examples. The docs are explicit, though, that "it is not intended to perform the task of speaker verification directly" ([openWakeWord verifier docs](https://github.com/dscripka/openWakeWord/blob/main/docs/custom_verifier_models.md)).

### Calibrate on the exact capture chain the assistant will use

No published calibration procedure for voice assistants was found, so the recipe here is assembled from the tools the sources document, and it doubles as the design for the in-progress calibration task.

It starts with device selection. Enumerate input devices through WASAPI and open the chosen mic in shared mode with `auto_convert`, which lets Windows resample to 16 kHz without locking the mic away from OBS or Discord ([sounddevice WASAPI settings](https://python-sounddevice.readthedocs.io/en/latest/api/platform-specific-settings.html)). Steer the owner toward the raw physical mic, or the NVIDIA Broadcast virtual mic if they use RTX denoise, and warn against mixer output buses such as a Wave Link or Voicemeeter "Stream Mix", which carry game audio, Discord and the assistant's own TTS. Persist the device by name as well as index, since indices shift when USB devices re-enumerate.

The wizard then records several seconds of the owner's normal environment and several seconds of normal speech, sets the VAD threshold between the two, and warns when speech barely clears the noise floor or clips. Next come 5–10 wake-word takes (normal, quiet, shouted, and with a game running), which serve as verifier positives, enrollment embeddings and a check that the wake model actually fires on this owner's pronunciation. Impostor audio comes last: Discord voices, YouTube and stream audio captured through WASAPI loopback ([PyAudioWPatch](https://github.com/s0d3s/PyAudioWPatch)), plus synthetic voices of the kind OVOS's tests use. The threshold should sit where the owner's genuine scores clear it with a small margin and almost all impostor scores fall below.

Store which model produced each embedding, because embeddings do not transfer between models. Re-run calibration whenever the mic, the noise suppression or the model changes. Show live verifier scores in the HUD so the owner can see why a command was dropped.

### Echo: gate first, cancel second

Handle echo in three tiers. **Tier 1 is an echo gate, always on.** While TTS plays and for a short tail afterwards, drop any transcript that closely matches the words being spoken, using the check that fixed hermes-agent. Add a breaker that stops repeated near-identical turns. EdgeVox shows how to tune the gate. It requires mic energy at least **3x the last speaker-output level**, about **250 ms of sustained speech**, and a **1.5 s cooldown** after TTS ends ([EdgeVox interrupt docs](https://github.com/nrl-ai/edgevox/blob/main/docs/documentation/interrupt.md)).

**Tier 2 is real acoustic echo cancellation (AEC) for speaker users.** Capture the system audio output through WASAPI loopback and use it as the reference for WebRTC AEC3 on the mic stream. `pywebrtc-audio` ships AEC3, noise suppression and automatic gain control with Windows x86_64 wheels for Python 3.10–3.14 ([pywebrtc-audio](https://github.com/strands-labs/pywebrtc-audio)). `echoff` (MIT, alpha) handles the hard part: loopback capture and aligning the two device clocks onto one timeline. It reports the echo path as ready after 7.5 s of reference audio and at least 10 dB of reduction ([echoff](https://github.com/KoljaB/echoff)). WebRTC's AEC is linear and struggles with delays over about 500 ms ([LiveKit community](https://community.livekit.io/t/server-side-echo-cancellation-on-pstn-audio-advice-delay-limits-and-recommended-config/1789)). Using the whole system output as the reference, rather than just the TTS buffer, also cancels game audio, music and Discord played through speakers. That helps both wake-word false accepts and speaker verification.

**Tier 3 covers headphone users.** Strands' implementation disables AEC for headsets, since there is no acoustic echo ([strands audio.py](https://github.com/strands-agents/harness-sdk/blob/main/strands-py/src/strands/experimental/bidi/audio.py)).

Do not count on Windows Voice Clarity. Discord, Teams and Zoom open their capture in RAW mode, which bypasses system echo cancellation ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/5783329/why-do-communication-apps-teams-discord-default-to)).

### Noise suppression: keep it moderate, and don't expect it to remove other voices

WebRTC noise suppression in `pywebrtc-audio` offers levels 0–3, which suppress 6, 12, 18 or 21 dB. It is the cheapest option because it comes in the same pipeline as AEC. RNNoise adds only about 10 ms of latency but is weak on non-stationary noise, while DeepFilterNet3 offers the best open quality and now runs as ONNX without PyTorch at a real-time factor of about 0.145 with 32 ms of latency ([deepfilter-stream](https://github.com/wuxuedaifu/deepfilter-stream); [Forasoft comparison](https://www.forasoft.com/learn/ai-for-video-engineering/articles-ai/real-time-noise-suppression-krisp-rnnoise-deepfilternet)); add it only if residual game or keyboard noise measurably hurts wake-word or STT accuracy.

None of these free options removes competing speech: "Other humans speaking nearby need to be muted? Krisp. There's no free equivalent" ([pipecat-deepfilternet write-up](https://github.com/vahidkowsari/pipecat-deepfilternet-stream/blob/main/MEDIUM.md)). NVIDIA's audio effects do list "Chatter from other people" among the noises they remove, and staff suggest about 75% intensity ([NVIDIA AFX guide](https://docs.nvidia.com/deeplearning/maxine/audio-effects-sdk/index.html); [NVIDIA forum](https://forums.developer.nvidia.com/t/audio-effect-sdk/187114)). On an RTX machine, the zero-code integration is to select the NVIDIA Broadcast virtual mic as the assistant's input.

Keep suppression moderate. Enroll through the same chain used at runtime, because heavy processing shifts both speech recognition and speaker embeddings.

### A convenience filter, not a lock

Voice matching is not a security boundary. Assistant vendors do not offer voice profiles as a security feature "due to the number of false positives". In tests, devices failed to tell recorded, replayed and synthetic voices from real ones ([Valero Amores et al.](https://exa.ai/library/publication/cfdqsg1k4n6)). Replay is described as among "the easiest to perform" attacks ([DataBreachToday](https://www.databreachtoday.asia/hey-alexa-this-my-voice-or-recording-a-14562)).

For a streamer the replay source is built in: their own VODs, clips and re-streams. Speaker verification's real value here is different. It blocks commands spoken by *other* voices: YouTube videos, Discord friends, and text-to-speech in chat alerts. That also makes it a defence against injecting instructions through audio.

Embeddings are biometric-derived data. Anonymised speaker embeddings (x-vectors) have been inverted to re-identify about 60% of speakers (top-1) ([Champion et al.](https://ar5iv.labs.arxiv.org/html/2110.05431)). Store embeddings locally and encrypt them with Windows DPAPI. Offer delete and re-enroll controls. Keep a second factor for anything consequential.

## Kokoro and abort()-based playback make replies feel immediate

SAPI and pyttsx3 give the app only the legacy Windows voices. Windows 11's natural Narrator voices (en-GB Ryan among them) are not exposed to third-party apps. The only route to them is NaturalVoiceSAPIAdapter, which "uses some encryption keys extracted from system files … more like a hack" ([NaturalVoiceSAPIAdapter](https://github.com/gexgd0419/NaturalVoiceSAPIAdapter)).

**Kokoro-82M** is the right free local default. Its weights are Apache-2.0 and it installs with `pip install kokoro-onnx` (MIT wrapper). It scores **Elo 1060** on the Artificial Analysis arena, above Azure Neural (1029) and XTTS-v2 (922) ([Kokoro card](https://huggingface.co/hexgrad/Kokoro-82M); [kokoro-onnx](https://github.com/thewh1teagle/kokoro-onnx); [Artificial Analysis](https://artificialanalysis.ai/text-to-speech/leaderboard)).

Kokoro is fast on GPU but only about **2x real time on a CPU**. Its best British male voices, `bm_george` and `bm_fable`, grade only C. It is also weak on utterances under about 10–20 tokens ([Kokoro VOICES.md](https://huggingface.co/hexgrad/Kokoro-82M/blob/main/VOICES.md)). The practical design therefore streams Claude's output through a sentence splitter that keeps the first chunk short but not tiny, warms the model at startup (on an RTX 4090 the first cold synthesis took 2.44 s and warm ones 47 ms ([GigaGPU benchmarks](https://gigagpu.com/tts-latency-benchmarks/))), and keeps pyttsx3 as the zero-dependency fallback. Avoid the higher-ranked open models as defaults: Fish Audio S2 Pro ships under a research licence and wants a 24 GB GPU, Voxtral TTS weights are CC BY-NC, Breeze TTS 2 is non-commercial, and XTTS-v2's CPML licence has no one left to sell a commercial exception ([fish.audio](https://fish.audio/s2/); [Mistral](https://mistral.ai/news/voxtral-tts/); [MindStudio](https://www.mindstudio.ai/blog/breeze-tts-2-license-commercial-use); [LocalAIMaster](https://localaimaster.com/blog/xtts-coqui-commercial-license)).

Playback needs one persistent `sounddevice.OutputStream`, fed from a queue. `Stream.stop()` "waits until all pending audio buffers have been played"; `abort()` terminates immediately ([sounddevice docs](https://python-sounddevice.readthedocs.io/en/0.5.3/api/streams.html)). Deepgram calls using `stop()` "the single most common bug in a first voice agent". At least two queues sit between the agent and the speaker, and "clearing one is not enough" ([Deepgram workshop](https://workshops.deepgram.com/voice-agent-py/barge-in)). Barge-in should stop playback, flush every queue and cancel the Claude stream within the **~100 ms** that real-time pipeline guides budget ([ai-engineering-from-scratch](https://raw.githubusercontent.com/rohitg00/ai-engineering-from-scratch/main/phases/06-speech-and-audio/11-real-time-audio-processing/docs/en.md)). Then keep only the words that were actually heard, following Open-LLM-VTuber.

Do not clone Paul Bettany's voice. ElevenLabs bans replicating "the voice of another person without consent" ([ElevenLabs use policy](https://elevenlabs.io/use-policy)), Tennessee's ELVIS Act covers "simulations" of a voice ([Holland & Knight](https://www.hklaw.com/en/insights/publications/2024/04/first-of-its-kind-ai-law-addresses-deep-fakes-and-voice-clones)), and a New York court let voice actors' publicity claims proceed in *Lehrman v. Lovo* ([Skadden](https://www.skadden.com/insights/publications/2025/07/new-york-court-tackles-the-legality-of-ai-voice-cloning)). Get the JARVIS feel from a dry British stock voice or a designed voice, plus the script. Do not hard-code ElevenLabs "Default" voice IDs; those voices expire on December 31, 2026 ([ElevenLabs docs](https://elevenlabs.io/docs/help-center/product/voices/my-voices/what-are-default-voices)).

## PC control should go API first, accessibility tree second, pixels last

The benchmark evidence points one way. On WindowsAgentArena (154 tasks) the baseline agent reached **19.5%** against **74.5% for humans**, and agents using only pixels and OCR did worse than those that also read the UIA tree ([WindowsAgentArena, ICML 2025](https://proceedings.mlr.press/v267/bonatti25a.html)). Microsoft's UFO² keeps every control UIA can see and adds vision-detected controls only where UIA sees nothing, which "consistently outperforms either UIA-only or OmniParser-only settings" and converts up to 9.86% of previously failed cases into successes ([UFO² paper](https://arxiv.org/html/2504.14603)). Agent S3 credits "programmatic edits over direct GUI manipulation" and reaches **50.2% on WindowsAgentArena, or 56.6% with best-of-3** ([Agent S3](https://github.com/simular-ai/agent-s/blob/main/README.md)), and OpenAI now recommends a code-execution harness over raw clicks ([OpenAI computer use](https://developers.openai.com/api/docs/guides/tools-computer-use)). Frontier models score 75–86% on the Linux-based OSWorld-Verified, according to aggregators that disagree with one another ([BenchLM](https://benchlm.ai/benchmarks/osworld-verified)), yet the best open framework still fails about half of Windows multi-app tasks. Agentic GUI mode therefore belongs to the long tail, not to everyday commands.

UIA pattern calls (Invoke, SetValue, Toggle) have a property that matters for reliability. When an elevated window has focus, Windows drops all synthetic input from a normal-privilege process, but "UIA pattern calls, screen capture and OCR keep working perfectly". Chromium 138+ now exposes native UIA by default ([Chrome blog](https://developer.chrome.com/blog/windows-uia-support-update)). Tk widgets, canvas-drawn UIs and games still expose little or nothing to UIA.

For the long tail, the configured `claude-opus-5` supports `computer_toolset_20260801`. One entry gives Claude **17 member tools** (screenshot, left_click, type, zoom and more) with no beta header. An optional `configs` map turns individual members on or off. Claude can return several actions in one response, called a batch. The app must run them in order and stop at the first failure, and "make that check before each block runs" if a human confirms consequential actions ([Claude computer use docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool.md)).

The reference implementation is a Linux Docker container, so the Windows side needs its own executor: screenshots taken with `mss` and downscaled to around 1280×800 (WXGA), since the quickstart advises against sending anything larger ([computer-use-demo](https://github.com/anthropics/anthropic-quickstarts/blob/main/computer-use-demo/README.md)); coordinates rescaled back to the real screen; clicks delivered through UIA or `SendInput`; and each run capped at 25 steps and 3 consecutive failures, following Windows-Use's defaults.

OmniParser v2 adds vision grounding at 0.8 s per frame on an RTX 4090. Its original icon detector is AGPL-3.0; the newer `icon_detect_v3` is MIT ([OmniParser card](https://huggingface.co/microsoft/OmniParser-v2.0/blob/main/README.md)). Skip it until Claude's own grounding plus `zoom` proves insufficient.

Safety has to come before capability, because prompt injection from screen content is not solved. Anthropic measured about a **1% attack success rate** for Claude Opus 4.5 against an adaptive attacker in browser use and says "No browser agent is immune" ([Anthropic](https://www.anthropic.com/research/prompt-injection-defenses)). A reading of the Opus 4.8 system card reports **31.5% raw per-attempt success, falling to 0.5% with safeguards**; the same article claims the API ships without the full safeguard stack, while Anthropic's docs say injection classifiers run automatically on computer-use prompts ([VentureBeat](https://venturebeat.com/security/anthropic-browser-agent-hijacked-31-percent-before-safeguards-engaged)), a conflict this research could not resolve. Adversarial pop-ups reached an **86% mean attack success rate**, and "ignore pop-ups" prompts did not help ([CSA Labs](https://labs.cloudsecurityalliance.org/research/csa-research-note-computer-use-agent-safety-blindspots-20260/)). OWASP's guidance is least-privilege tools, explicit authorization for sensitive operations, and treating all external data as untrusted ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html)).

Tier every tool:

| Tier | What it covers | Confirmation |
|---|---|---|
| T0 | Read-only actions | Runs automatically |
| T1 | Reversible actions: volume, brightness, opening apps, switching scenes | Runs automatically |
| T2 | Typing into apps, closing apps that may have unsaved work, changing settings | Spoken or toast-button confirmation |
| T3 | Deleting, sending, purchasing, running shell commands, starting or stopping the stream | Confirmation for every single action, with the exact target read back |

Beyond the tiers, deny the agent access to password managers, UAC prompts and banking windows, and let it act only on the verified owner's utterance, never on text read from the screen, notifications or toasts. Add a global kill hotkey, write every action to an append-only JSONL audit log, and keep the main process non-elevated in the user's session; a non-elevated process cannot inject input into elevated windows, which shrinks the blast radius of any successful injection. Windows' own Agent Workspace, a contained, policy-controlled desktop for agents, is still an admin-enabled preview ([Microsoft Support](https://support.microsoft.com/en-us/windows/experimental-agentic-features-a25ede8a-e4c2-4841-85a8-44839191dfb3)).

## Streaming automation: deepen OBS and delegate platforms to Streamer.bot

**OBS.** The assistant already uses the basics of obs-websocket v5, but the protocol exposes far more ([obs-websocket protocol](https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md)). `RequestBatch` runs multi-step macros serially with `haltOnFailure`, so "hide webcam, switch scene, mute mic" becomes one atomic voice command. The event stream is the bigger gap: `StreamStateChanged` reports `RECONNECTING`, so the assistant can announce a dropped stream immediately; `ReplayBufferSaved` returns the saved file path, which can feed straight into a clip pipeline; and `InputVolumeMeters` reports every input's level every 50 ms once explicitly subscribed, which, downsampled to a rolling one-second level, catches a silent or clipping mic. `SetSceneItemEnabled`, `SetSourceFilterEnabled` and `TriggerMediaInputAction` cover "hide the cam", "blur on" and "play the intro"; `CreateRecordChapter` marks moments in Hybrid MP4 recordings; `SendStreamCaption` turns the assistant's STT into live captions; and `GetSourceScreenshot` gives Claude eyes on the stream.

For the client library, `simpleobsws` (MIT, async) fits a FastAPI backend. `obsws-python` is synchronous, GPL-3.0, and "Not all endpoints ... are implemented" ([simpleobsws](https://github.com/IRLToolkit/simpleobsws); [obsws-python](https://github.com/aatikturk/obsws-python)). Make "clip that" a zero-LLM fast path, and confirm stream start and stop as obs-mcp does.

**Stream health.** Guides converge on three thresholds for dropped frames: **up to 0.1% is imperceptible, above 0.5% shows artifacts, and above 2% degrades noticeably**. They also recommend keeping bitrate under about 70% of measured upload ([Livepush](https://livepush.io/blog/obs-dropped-frames-fix/)). Twitch's advice for network drops is to lower the bitrate by 200–500 kbps ([Twitch broadcast health](https://help.twitch.tv/s/article/guide-to-broadcast-health?language=en_US)). The watchdog should compute changes over time (not cumulative totals) from `GetStats` and `GetStreamStatus`, separating network drops, encoder skips and render lag. Each class has a different fix, and the assistant can say which one applies.

**Twitch.** PubSub was shut down on April 14, 2025 ([Twitch lifecycle](https://dev.twitch.tv/docs/product-lifecycle/)). EventSub over WebSocket now carries follows, subs, bits, raids, redemptions, hype trains and chat; it requires a user access token, subscriptions must be made within 10 s of connecting, and events missed during a disconnect are not replayed, so the assistant must rebuild state on reconnect ([Handling WebSocket events](https://dev.twitch.tv/docs/eventsub/handling-websocket-events/)). For auth, Twitch recommends the device-code flow as a *public* client with no client secret for apps "on a more open platform (such as windows)"; access tokens last 4 hours and refresh tokens are single-use ([Twitch OAuth](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/)).

Voice commands map onto single Helix calls. Create Clip gained `title` and `duration` parameters in December 2025, which makes "clip the last 30 seconds, call it X" possible ([Twitch changelog](https://dev.twitch.tv/docs/change-log/)). Stream markers, title and category changes, ads (broadcaster only, affiliates and partners only), shoutouts, polls and predictions each need a scope listed on Twitch's scopes page ([Twitch scopes](https://dev.twitch.tv/docs/authentication/scopes/)). TwitchIO 3.3.2 (August 2026) is actively released; twitchAPI 4.5.0 is more complete but was last released in May 2025 ([TwitchIO](https://pypi.org/pypi/twitchio/json); [twitchAPI](https://pypi.org/pypi/twitchAPI/json)).

**YouTube.** Use `liveChatMessages.streamList` instead of polling. Polling `list` costs about 5 units per call against a default quota of 10,000 units per day, which lasts about 33 minutes at one request per second ([streamList](https://developers.google.com/youtube/v3/live/docs/liveChatMessages/streamList); [Stack Overflow](https://stackoverflow.com/questions/67232262/how-much-quota-cost-does-the-livechatmessages-list-method-incur)).

**Kick.** Kick's public API delivers events by webhook only, and webhooks need a public HTTPS URL ([Repostit](https://repostit.io/how-to-build-a-kick-chat-bot/)). A local app therefore needs a tunnel (cloudflared or ngrok) or a delegate such as Streamer.bot. Kick also discards chat after a stream ends, so chat must be recorded locally to score highlights later ([clips-studio](https://github.com/ColinGPT9/clips-studio)).

**Streamer.bot as the multi-platform layer.** `POST http://127.0.0.1:7474/DoAction` runs any action by ID or name with arguments ([Streamer.bot HTTP](https://docs.streamer.bot/api/http/requests/do-action)). The WebSocket server on port 8080 streams events back ([configuration](https://docs.streamer.bot/api/websocket/guide/configuration)). The official client can wait for an action to finish and return values ([Streamer.bot client](https://streamerbot.github.io/client/guide/actions)), which lets the assistant speak the result, such as "your queue has 4 people". The division of labour is: the assistant owns voice and intent, native obs-websocket owns OBS, and Streamer.bot owns alerts, channel points and cross-platform chat.

**Other creator tools.** VTube Studio has an official WebSocket API on port 8001 and a Python client, `pyvts`, which makes "wave" or "angry face" a one-line hotkey trigger ([VTube Studio](https://github.com/DenchiSoft/VTubeStudio/)). Voicemod's Control API is technically simple but requires a partner `clientKey` issued by Voicemod ([Voicemod](https://control-api.voicemod.net/api-reference/)), and Wave Link 3.x has only a reverse-engineered protocol that "might break with future Wave Link updates" ([wavelink-ts](https://github.com/Raphiiko/wavelink-ts/blob/main/PROTOCOL.md)).

**Automatic highlights.** Open-source highlight tools agree that chat spikes are the best signal. ChrisTitusTech's tool flags spikes above 2 standard deviations, and its author calls them "the ground truth signal" ([live-clip-finder](https://github.com/ChrisTitusTech/live-clip-finder)). The assistant can do this live instead of on the VOD. On a chat-rate spike or a mic loudness spike, it saves the replay buffer and drops a marker. After the stream, it queues the saved file for Whisper, a Claude-written title and a 9:16 crop.

**AI co-host mode.** Neuro-sama's two-week ban for "hateful conduct" in January 2023 ([Kotaku](https://kotaku.com/neuro-sama-twitch-vtuber-ban-holocaust-minecraft-ai-1849977269)) and Twitch's rule that streamers are "responsible for ensuring that content that appears on your stream abides by" its guidelines ([Twitch guidelines](https://safety.twitch.tv/s/article/Community-Guidelines)) set the requirements for any co-host mode: filters on chat before it reaches the LLM and on the LLM's output before TTS, a human moderator, and a visible kill switch.

The ordering follows the dependencies. Speaker verification is only as good as the short audio segments the VAD hands it, trigger words need the keyterm-capable recognizer, and safe PC control needs both a verified speaker and a fast confirmation channel in the form of interruptible TTS or a toast button. The Phase 5 OBS work is independent, low-risk and high-value for a streamer, so it can run in parallel with Phase 1.

Almost every latency and accuracy figure above was measured by the vendor, and usually on Linux, Mac or datacenter hardware. The first thing to build is therefore a small benchmark: about 50 of the owner's real commands, plus an hour of game, Discord and stream audio with no commands in it. Run it on the actual PC to measure WER, false wakes per hour, missed wakes, time from end of speech to text, and time to first audio. Let those numbers, not the vendors', set the tier defaults and thresholds.

## Conclusion

The licensing ground moved in 2026. Porcupine closed its free tier. Piper moved to GPL-3.0. openWakeWord's pretrained models are non-commercial. Several of the best-ranked open TTS weights (Fish S2 Pro, Voxtral, Breeze) carry non-commercial terms. The "free defaults" in 2024-era JARVIS tutorials are now either unavailable or encumbered. Self-trained trigger models running on MIT or Apache runtimes are the clean path, and for this app they also turn out to be the most capable one.

For a streamer, the hardest impostor for "only my voice" is the owner. Their voice is broadcast, clipped and replayed, and they mention the assistant to chat constantly. Owner-only listening therefore needs two partners: "only when addressed" (a wake word anchored to the start of the utterance, with two stages) and "only with confirmation when it matters" (risk tiers). Speaker verification's biggest practical payoff is blocking other voices: videos, Discord and chat text-to-speech. That makes it an injection defence as much as a personalization feature.

The fragile parts of the plan sit in undocumented Windows and platform interfaces: IPolicyConfig, pyvda's COM calls, WNF for Do Not Disturb, edge-tts, Wave Link and Kick's unofficial socket. Each belongs behind a feature check in the existing doctor, with a graceful fallback. This research did not measure Claude API latency.
